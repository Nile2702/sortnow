# Monetization & Billing Engine (India-specific)

## 1. Pricing tiers

| Tier | Monthly price (illustrative) | SKU limit | Features |
|---|---|---|---|
| **Lite** | ₹499/mo | up to 100 SKUs | 1 theme, path-based URL only, basic analytics |
| **Pro** | ₹1,999/mo | up to 2,500 SKUs | Full Theme Studio, subdomain, live-sale broadcast, WhatsApp notifications, QR standee generator |
| **Max** | ₹6,999/mo (+ metered above 25,000 SKUs) | up to 25,000 SKUs | Custom domain, multi-store (chains), bulk CSV import, priority search ranking, dedicated support |
| **Overage / fallback metering** | ₹2 per listing beyond tier cap | — | Applied when a merchant temporarily exceeds their tier's SKU cap instead of hard-blocking uploads |

Billed monthly or annually (annual = ~2 months free) via `subscriptions`
table (`database/schema.sql`), each linked to a Razorpay/Cashfree
`subscription_id`.

## 2. Recurring billing — UPI AutoPay & cards

- **Primary PSP:** Razorpay Subscriptions (supports UPI AutoPay e-mandate,
  cards, net banking natively; NPCI-compliant e-mandate framework for
  recurring debits ≤ ₹15,000 without additional factor auth, matching
  typical Lite/Pro pricing).
- **Secondary/fallback PSP:** Cashfree (used for merchants whose bank
  rejects Razorpay's mandate registration, or for load balancing).
- Flow: merchant picks a plan → backend creates a PSP `plan` + `subscription`
  → merchant redirected to PSP checkout to authorize UPI AutoPay mandate or
  save a card → PSP webhooks drive all subsequent lifecycle state (see
  `services/billing/webhook-listener.ts`).
- **Dunning:** on `subscription.charged.failed`, retry per PSP's own retry
  schedule; after N failures, `subscriptions.status = 'past_due'` →
  merchant portal access degrades to read-only after a grace period (see
  §4) → `subscriptions.status = 'cancelled'` after grace period expiry.

## 3. Metering (per-listing fallback fee)

For merchants who briefly exceed their SKU cap (e.g., seasonal stock-up)
instead of blocking the bulk upload:
1. Catalog Service checks `count(products where store_id=X and active=true)`
   against `plans.sku_limit` on each publish.
2. Overage SKUs are still published (never break the merchant's business)
   but flagged `billing_metered = true`.
3. A nightly job aggregates metered SKU-days into a `usage_records` table;
   Billing Service creates a Razorpay one-off "addon" charge on the next
   invoice cycle (Razorpay Subscriptions supports `addons` for exactly this).

## 4. Access restriction on lapse

State machine on `subscriptions.status`:

```
trialing → active → past_due (grace: 7 days, portal read-only banner)
                        │
                        ├─→ active (payment recovered)
                        └─→ suspended (storefront still live for shoppers,
                                        seller portal locked to billing page only)
                                │
                                └─→ cancelled (after 30 days suspended:
                                    storefront shows "temporarily unavailable",
                                    data retained 90 days before purge)
```

Enforcement is a single `SubscriptionGuard` middleware in the API Gateway
checked on every Seller Portal request (not per-microservice, to keep the
rule in one place) — it reads a cached `subscriptions.status` (Redis,
30s TTL) keyed by `store_id`.

## 5. GST-compliant invoicing

- Each subscription charge produces a `gst_invoices` row computed from:
  - **Place of supply** = merchant's registered state (from GSTIN, first 2
    digits = state code) vs. **platform's registered state** (SORT IT OUT's
    home state).
  - If same state → **CGST + SGST** (each half of the applicable GST rate,
    e.g. 9% + 9% for 18%).
  - If different state → **IGST** (full 18%) — the common case since the
    platform is centrally registered while merchants are pan-India.
- Invoice PDF generated by the async **Invoice Generator** worker
  (triggered off `invoice.generated` event from Billing Service), using a
  GST-compliant template (invoice number sequence, HSN/SAC code for SaaS
  services, GSTIN of both parties, tax breakup table) — stored in S3, linked
  from `gst_invoices.pdf_url`, emailed to the merchant.
- `hsn_sac_code` for the SaaS subscription line item stored on the `plans`
  table (SAC 998319 — "Other IT services" is typical for SaaS; platform
  should confirm exact code with a CA before launch — flagged here as a
  compliance checkpoint, not a code decision).

## 6. Webhook reliability

- All PSP webhooks are verified via HMAC signature (Razorpay:
  `x-razorpay-signature` header against the webhook secret) **before** any
  processing — see `services/billing/webhook-listener.ts`.
- Webhook handler writes the raw event to a `webhook_events` table
  (idempotency key = PSP event id) inside the same transaction as the state
  change, so replayed/duplicate webhooks (PSPs retry on non-2xx) are no-ops.
- Long-running side effects (invoice PDF, notification) are pushed to the
  event bus rather than done inline in the webhook handler, so the handler
  returns 200 fast and PSP doesn't retry unnecessarily.
